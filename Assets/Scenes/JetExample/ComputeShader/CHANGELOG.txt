Сцена SmokeMaze2D — 2D-лабиринт распространения дыма (вид сверху XZ)
====================================================================
ScenarioType.SmokeMaze2D: упрощённая схема по эскизу — источник слева (оранжевый),
3 перегородки с разными проходами (синие), вытяжка справа сверху (зелёная).

- BuildMazeWallMask: внешние стены + 3 вертикальные перегородки со смещёнными проёмами;
  источник и вытяжка исключены из маски стен.
- Геометрия wall2/wall3 раскрыта шире: исходная wall2 почти полностью перекрывала средний канал
  после wall1 и создавала стабильный затор вместо распространения дыма.
- ApplyJetBoundary: стены k=0; вытяжка по умолчанию не задаёт фазовый jet
  (_mazeVentSuction = 0), чтобы не создавать обратную компенсационную циркуляцию;
  источник — опциональный jet (_mazeEmitVelocity, по умолчанию 0 — без «лазерной ленты»).
- DriftMazeTowardVent: слабый продольный поток +X без маршрутизации через стены.
- SmokeMaze2D diagnostics: Console-метрики распределения частиц по секциям/стенам/вытяжке.
- DisperseMazeParticles: умеренное турбулентное рассеивание трассеров в XZ для поиска смещённых проходов.
- Частицы спавнятся в источнике; в зоне вытяжки удаляются (CompactMazeParticles).
- Исправление стен: InterpolateVelocity с clamp (не toroidal wrap); PushParticlesOutOfSolidMask
  + ClampPositionsToVolume; маска стен по углам ячеек; двойной ApplyJetBoundary на стенах.
- Домен 5×1×3 (тонкий по Y — «2D»), меню «ShrodingerFlow/Create Smoke Maze 2D Scene».


Аудит ISF Compute Shader — исправления и оптимизации
=====================================================

BUG 1 (КРИТИЧЕСКИЙ): Ненормализованные веса трилинейной интерполяции
---------------------------------------------------------------------
Файл: SFComputeParticles.compute, ядро InterpolateVelocity

Проблема: Веса интерполяции wx, wy, wz лежали в диапазоне [0, dx) вместо [0, 1).
При dx = 0.0625, частица на 80% пути между узлами получала вес 0.05 вместо 0.8.
Интерполяция вырождалась в quasi-nearest-neighbor — частицы двигались грубо
с сеточными артефактами вместо плавных траекторий.

Баг унаследован из оригинального CUDA (update_velocities.cu).

Исправление: wx = (tmp_x - ix * _TorDX) / _TorDX  (аналогично для wy, wz).


BUG 2 (ФИЗИЧЕСКИЙ): AddTurbViscosity вычисляет не то
-----------------------------------------------------
Файл: SFComputeLES.compute, ядро AddTurbViscosity

Проблема: Код вычислял Laplacian(nu_t) (лапласиан самой турбулентной вязкости)
и добавлял одно и то же скалярное значение ко всем трём компонентам скорости.
Стандартная модель Smagorinsky требует nu_t * Laplacian(u_i) — вязкую диффузию
самой скорости. Вместо затухания мелкомасштабных вихрей добавлялся градиент
градиента вязкости — физически бессмысленная операция.

Баг унаследован из оригинального CUDA (add_turb_viscosity.cu).

Исправление: Для каждой компоненты (U, V, W) отдельно вычисляется Laplacian(u_i),
затем применяется dt * nu_t_center * Laplacian(u_i).


BUG 3 (SAFETY): Отсутствие защиты от отрицательных индексов
------------------------------------------------------------
Файл: SFComputeParticles.compute, ядро InterpolateVelocity

Проблема: Если позиция частицы становилась отрицательной (из-за численной ошибки),
floor(pos/dx) давал отрицательный ix. Значение ixp = (ix+1) % Res было обёрнуто,
но сам ix использовался для индексации буфера без проверки — out-of-bounds доступ.

Баг унаследован из оригинального CUDA.

Исправление: Добавлен periodic wrap: ix = ((ix % ResX) + ResX) % ResX
(аналогично для iy, iz).


BUG 4 (MINOR): Подозрительный sign-flip в VelocityOne
------------------------------------------------------
Файл: SFComputeKernels.compute, ядро VelocityOne

Проблема: Когда мнимая часть скалярного произведения близка к нулю,
код выполнял r *= -1 (инверсию знака угла). Физической мотивации нет —
это хак из оригинального CUDA для подавления шума, но он мог инвертировать
скорость на границах вихрей.

Баг унаследован из оригинального CUDA (velocity_one.cu).

Исправление: Заменено на r = 0.0 — обнуление скорости вместо инверсии.


PERF 1: Аллокация временных буферов каждый кадр
------------------------------------------------
Файл: CSParticles.cs, метод AddParticles

Проблема: Каждый вызов AddParticles (каждый кадр) создавал и уничтожал
3 ComputeBuffer — лишняя нагрузка на аллокатор GPU.

Исправление: Staging-буферы (_stagingX/Y/Z) предаллоцированы и переиспользуются.
Расширяются через EnsureStagingCapacity() только если нужен больший размер.
Освобождаются в Dispose().


PERF 2: GPU обрабатывает все частицы, включая вылетевшие
--------------------------------------------------------
Файлы: CSParticles.cs + SFJetCS.cs

Проблема: Счётчик _size только рос. GPU считал RK4 для всех 50000 частиц,
даже если 90% вылетели за пределы объёма.

Исправление: Добавлен метод CompactParticles() — читает позиции с GPU,
отсеивает вылетевшие за пределы частицы, перезаписывает GPU-буферы
компактным списком живых частиц. Вызывается каждые 60 кадров из SFJetCS.
